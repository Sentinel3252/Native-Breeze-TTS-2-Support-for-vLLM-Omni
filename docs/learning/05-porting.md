# 5. 适配其他模型的步骤

[← 适配验证](04-correctness.md) · [学习指南](../learning-guide.md) · [项目首页](../../README.zh-CN.md)

适配其他模型时，可以沿用本项目的分析顺序和验证方法。
Breeze 的阶段划分、完整帧反馈和 Mimi 解码方式，则需要根据新模型重新决定。

## 1. 确定参考版本和支持范围

固定官方代码与 checkpoint revision，选择一条可复现的推理分支，
记录输入、输出和采样设置。先说明准备支持哪些功能，避免在实现过程中混入其他分支。

本项目先处理 S0 的文本与指令合成，参考音频、多说话人和多分支 CFG 留待后续。
其他模型也可以先支持较小的范围，但公开接口应明确拒绝尚未实现的参数。

## 2. 看清生成过程

沿官方代码确认：条件在哪里加入，每一步输出什么，下一步使用什么，何时停止。
同时整理数据形状，以及跨步保存的缓存和历史。

Breeze 一步生成完整 RVQ 帧，下一步使用所有码本 embedding 的和。
另一模型可能反馈单 token，也可能使用连续 latent。
这些差异决定了模型接口和传输数据，不能仅凭 backbone 结构相似就照搬实现。

## 3. 选择框架接口和阶段

标准的逐 token 自回归模型，可以先检查已有 vLLM 模型层和权重 loader 能否复用，
并核对 attention、归一化、RoPE、embedding 和输出 head 的计算。
需要后续模态处理的模型，再考虑 vLLM-Omni 的阶段编排和输出接口。

按计算依赖决定阶段划分。Breeze 的 Depth 影响下一步 AR 输入，
因此与 backbone 放在同一阶段；只消费生成结果的后处理则可以独立执行。
额外计算依赖当前采样结果时，需要找到合适的采样后回调。
扩散或迭代细化等模型还需要确认框架是否有对应的执行方式。

## 4. 注册配置并加载权重

建立配置、architecture 名称与原生模型类的对应关系。
使用多阶段 pipeline 时，还要注册阶段配置、输入来源和输出类型；
提供服务 API 时，再接入相应的请求 adapter。

逐项核对原生模块与 checkpoint 参数的名称和形状。
拆分到不同阶段的权重应有明确的加载范围，融合参数需要检查所有来源分片，
共享参数和持久 buffer 也要处理。完成加载后，再开始计算对照。

## 5. 接通请求并处理状态

从一个请求开始，确认提示能到达模型、生成结果能传到后续阶段、最终输出能返回调用者。
对每个跨步状态记录保存位置、请求标识、更新时机和清理入口。

再检查框架调度带来的情况：批处理中请求顺序变化、KV 抢占后的重放、
分块边界、取消和异常。Breeze 保存完整帧历史，是为了重放时不必重新采样 Depth。
其他模型是否需要类似历史，要看它的计算能否按原有结果重建。

## 6. 对照结果，再扩展功能

按配置和权重、输入条件、主模型计算、后处理、最终输出的顺序对照参考实现，
发现差异时从最早分歧处排查。
单请求通过后，再验证分块、并发、取消和资源清理。

正确性确认后，才有条件评价性能和增加优化。
每增加一种执行方式或输入分支，都应补充相应验证。
例如单分支结果一致，并不能说明 CFG、多说话人或参考音频也已支持。

## 发布时说明什么

文档应列出支持范围、checkpoint 与环境、启动方式、验证结果和已知限制。
如果修改了公共框架接口，还需要说明对已有模型的影响。
本项目的 [manifest](../../project-manifest.json)、[验证记录](../core-validation.md)
和[路线图](../roadmap.md)分别记录源码范围、已有结果和后续计划。

具体实现仍要依据新模型的配置、权重和参考代码。
例如占位文本 ID、采样后 Depth 回调、Mimi 的两帧尾部都是 Breeze 当前适配中的选择，
采用这些做法之前，需要先确认新模型是否有相同需求。
