以下内容可直接复制到后续对话。目标是推进 `0.2.0` 的三项代码工作；
`0.1.0` 的真实模型验收仍须按路线图完成，不能用版本号替代验证。

```text
请在当前 Breeze TTS 2 for vLLM-Omni 项目上继续开发，推进
0.2.0 的「Mimi 真正流式解码、Depth 批量解码、服务可靠性」。

先读取 README.md、README.zh-CN.md、project-manifest.json、
docs/architecture.md、docs/core-validation.md、docs/roadmap.md、
docs/releasing.md 和相关实现，确认实际进度，不要假设文档中的规划已实现。
当前记录的基线是 0.1.0-dev：基础合成链路已实现，有 CPU 数值和生命周期
回归测试；真实 checkpoint、Linux/CUDA 原生执行与完整服务仍待验证。

开始修改核心代码前，按发布指南保留当前源码快照及 SHA-256；若已有对应
快照，核对内容和校验和，禁止覆盖旧版本。当前根目录可能没有 Git，不能
把仅有的嵌套仓库 tag 当成整个项目的版本。若已经有完整源码根仓库，
按该仓库规范保留基线。日常维护同一份源码，不建立多份版本代码目录。

请实际完成以下工作，不要只给计划：

1. Mimi 真正流式解码
   在请求间隔离并持续维护 Transformer、卷积与上采样器所需状态，
   避免每个块都重新解码完整前缀。明确首块、中间块、尾块和空终止块
   的行为；保留前缀重解码作为可选参考/回退路径。使用真实小型 Mimi
   验证不同分块方式与完整解码的一致性、尾部完整性和请求交错行为。
   仅保留 Transformer KV cache 不足以宣称实现完整流式解码。

2. Depth 批量解码
   对兼容的活跃请求真正执行批量张量计算，支持不同进度与终止时间。
   保持请求独立的随机数状态、帧内 KV 状态和完整码本反馈。
   验证 greedy 数值一致性、固定 seed、批次重组、请求交错以及 EOS。
   不要把逐请求 Python 循环包装为批量解码。

3. 服务可靠性
   检查 AR、Depth、Mimi 和阶段传输的请求状态生命周期；补齐完成、
   取消、异常和资源上限触发时的清理及错误处理。为保留状态设置明确的
   资源边界，避免单个请求污染其他请求，禁止静默丢帧或丢音频。
   添加必要的诊断信息与有意义的回归测试，避免在日志中暴露用户输入。

优先保持基础 API 与模型行为兼容。真实权重或调度路径暴露的基础缺陷
应先修复；尚未验证的高级路径继续保持限制。本轮不扩展音色克隆、CFG、
多卡、量化或 CUDA Graph，它们属于后续版本。

按实际运行环境执行适当检查。具备 GPU 与 checkpoint 时，完成原生执行、
语音 API、流式、并发和取消的集成验证；若环境不具备，继续完成可验证的
代码与 CPU 检查，明确列出无法验证的部分，不伪造性能或模型可用性结论。
CPU 回调测试不能替代真实 vLLM 服务验收。

同步更新中英文 README、架构、API/配置说明、变更记录、版本路线及验证
记录；新增集成文件要加入 manifest。记录新的开发基线时使用 0.2.0-dev，
完成基础模型验收和本阶段验收后才发布 0.2.0，不提前宣称稳定或可用。
最后报告实际改动、测试结果、兼容性影响、剩余限制和版本快照位置。
```
